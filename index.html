01) Why message order matters

A conversation makes sense only when its messages appear in the right order. We explored how to preserve that order in a chat application, even when messages reach the receiver out of sequence. Our approach combines a FIFO queue, sequence numbers and a reorder buffer. Imagine Asha sends three messages to Ravi: “Hi!”, “Are you free?” and “Let’s meet.” These are messages 1, 2 and 3. If Ravi sees “Let’s meet” before “Hi”, the conversation feels confusing even though all three messages eventually arrive. Our goal is to preserve the sender’s intended sequence at the receiver. The important distinction is between arrival and display. We cannot force a delayed packet to arrive earlier, but we can decide when a received message becomes visible. A later message may be accepted into temporary storage without being displayed immediately. This solution handles one ordered sender stream. For a two-way chat, each direction can maintain its own sequence state. Establishing one shared order across messages from both users is a separate requirement.

02) Why messages can arrive out of order

Messages pass through networks, servers and application components before reaching the recipient. Different processing delays, retries, concurrent requests or reconnections can make a later application message available before an earlier one. For example, message 1 may require a retry while message 3 completes quickly. Be precise about the transport: TCP provides an ordered byte stream within one connection, and WebSocket messages on a single connection inherit that ordering. We do not need to repair packet ordering inside TCP ourselves. Application-level sequence numbers become useful when messages span multiple connections, independent operations, asynchronous workers or reconnect/replay paths. To explore application-level ordering, we consider a receiver whose input can arrive out of order. It might receive 3 → 1 → 2 even though the sender created 1 → 2 → 3. The receiver should ultimately display 1 → 2 → 3. A timestamp is not a reliable substitute for a sequence number. Clock differences and equal timestamps can make comparisons ambiguous. A sequence number directly identifies the intended position within a stream.

03) The structures we need

1. Sender FIFO queue FIFO means “first in, first out”. New messages join at the rear; the sender processes messages from the front. This preserves creation order locally. Assign a sequence number atomically when each message enters the stream so two simultaneous sends cannot accidentally receive the same number. 2. Sequence number Every message carries a positive integer: 1, 2, 3 and so on. The number belongs to a particular stream, not to all users globally. A practical message also carries a conversation identifier, sender identifier, session or stream identifier, and payload. 3. Reorder buffer Use a hash map whose key is the sequence number and whose value is the message. For example, {3: “Let’s meet”} means message 3 arrived but cannot yet be shown. A map lets us check directly whether the next expected message exists without sorting every arrival. 4. Expected sequence counter This stores the smallest sequence number that has not yet been displayed. It starts at 1 for a new stream. After displaying message 1 it becomes 2, and after displaying message 2 it becomes 3. 5. Display queue or ordered output Only messages released in consecutive order enter the visible chat. The UI may append them directly or consume an ordered queue. The key requirement is that displaying a batch must preserve the batch’s order. Queue operations and representation ENQUEUE adds a message at the rear. DEQUEUE removes the message at the front. FRONT reads the next message without removing it, and IS_EMPTY checks whether there is anything to send. A queue can be represented by a linked list with front and rear pointers, or by a circular array with front and rear indices. With a linked list, keep both pointers so insertion at the rear and removal at the front take O(1) time. A circular array reuses freed slots, but a fixed-size queue needs a full-capacity policy. Reorder-buffer operations The buffer is a map, not the sender FIFO queue. INSERT stores a message under its sequence number; CONTAINS checks whether a sequence is present; GET reads its message; REMOVE deletes it after release. The receiver asks for one exact key—expected—so it does not need to sort the entire map. Message record A message record contains stream_id, sequence and payload. The queue stores these records. At the receiver, stream_id selects the correct state, sequence selects the map entry, and payload supplies the text to display. The display queue receives records only after gaps have been filled.

04) The receiving algorithm, step by step

Step 1 — Identify the stream. Look up the receiver state for this conversation and sender stream. Each stream has its own expected counter and reorder buffer. Do not combine unrelated users’ sequence numbers in a single buffer. Step 2 — Check for an old duplicate. If the arriving sequence number is smaller than expected, the message was already released. Ignore it for display. A retry or replay can produce such duplicates; showing them again would repeat the conversation. Step 3 — Buffer a new arrival. If the sequence is not already in the buffer, store the message under that sequence number. A second copy of a buffered message should not create another entry. If two different payloads claim the same stream and sequence, treat that as a protocol conflict rather than silently replacing data. Step 4 — Release the consecutive prefix. While the buffer contains expected, remove that message, display it, and increment expected. Repeat because one arrival may unlock several messages that were waiting. Step 5 — Stop at a gap. As soon as expected is absent, stop releasing. Keep later messages buffered. This deliberate pause is what prevents a later message from overtaking an earlier one. All these state changes must be processed serially or protected by appropriate synchronization. Two concurrent handlers updating the same counter can otherwise introduce duplicates or lose updates.

05) A complete worked example

Suppose the sender creates: #1 — Hi! #2 — Are you free? #3 — Let’s meet. Before any arrival, expected = 1, the buffer is empty, and the receiver’s chat is empty. Arrival #3: store message 3. The buffer contains {3}. We still need message 1, so nothing is displayed. expected remains 1. Arrival #1: store message 1. Since the buffer now contains expected = 1, remove and display “Hi!”. Increment expected to 2. Message 2 is missing, so stop. Message 3 remains buffered. Arrival #2: store message 2. Remove and display “Are you free!”, then increment expected to 3. Message 3 is already present, so remove and display “Let’s meet.” Increment expected to 4. The final visible sequence is 1 → 2 → 3, although arrival order was 3 → 1 → 2. The buffer is now empty. If another copy of message 2 arrives, its number is less than expected = 4, so it is ignored. Notice that message 3 did not need to be resent merely because it arrived early. The reorder buffer retained it until the missing prefix became available.

06) Why the algorithm preserves order

The central invariant is: before each receive operation, every sequence number smaller than expected has already been released, and expected is the next sequence allowed to become visible. Initially expected = 1, so no messages have been displayed and the invariant holds. Receiving a later message only stores it; this does not change the visible order. Receiving an older duplicate leaves the state unchanged. The only release operation displays the message numbered exactly expected. It then increments the counter by one. Therefore every released message follows its predecessor. Repeating this operation releases a consecutive block, never a sequence with a gap. This establishes the safety property: the receiver never displays a later sequence before an earlier one within the same stream. It does not establish eventual delivery. For progress, the missing message must eventually arrive, usually through a retry mechanism. This is also why an ordinary FIFO receiver queue is insufficient. It preserves insertion order, but insertion order at the receiver is arrival order. Sequence numbers and the buffer supply the missing knowledge about send order.

07) Data-structure pseudocode

The following pseudocode describes abstract operations rather than a programming-language implementation. The sender uses a FIFO queue; the receiver uses a map as its reorder buffer and a FIFO queue for ordered display. State at the sender outgoing is an initially empty FIFO queue. nextSequence starts at 1. When the user creates a message, construct a record with its stream identifier, sequence number and text, then enqueue it. Increment nextSequence so the following message receives the next number. Sending removes records from the front of outgoing. State at the receiver Each sender stream has an initially empty buffer, an expected counter starting at 1, and an initially empty displayQueue. The buffer stores records by sequence number. The display queue stores only consecutive records that are ready for the interface. Reading the receive procedure A sequence below expected is an old duplicate. A sequence already buffered is a duplicate waiting behind a gap. Otherwise, insert it into the map. The WHILE loop then moves the consecutive prefix into displayQueue, stopping when the next expected key is missing. Why use WHILE instead of IF? One arrival can unlock several records. With message 3 buffered and expected = 2, receiving message 2 releases both 2 and 3. An IF would release only 2 and leave 3 unnecessarily waiting. Scope of the pseudocode Operations on the same stream are serialized. Sequence numbers are valid positive integers; stream identifiers are already validated. SEND_TO_NETWORK represents transmission, while DISPLAY represents appending to the chat. Retries, acknowledgements and durable commits are extensions discussed in the following sections.

Queue and reorder-buffer pseudocode

RECORD Message:
    streamId
    sequence
    payload

SENDER STATE (for one stream):
    outgoing ← EMPTY FIFO QUEUE
    nextSequence ← 1

PROCEDURE CREATE_MESSAGE(streamId, text):
    message ← Message(streamId, nextSequence, text)
    ENQUEUE(outgoing, message)
    nextSequence ← nextSequence + 1

PROCEDURE SEND_PENDING_MESSAGES():
    WHILE NOT IS_EMPTY(outgoing):
        message ← DEQUEUE(outgoing)
        SEND_TO_NETWORK(message)
        // Retain a retry copy if reliable delivery is required.

RECEIVER STATE (separate state for each stream):
    expected ← 1
    buffer ← EMPTY MAP
    displayQueue ← EMPTY FIFO QUEUE

PROCEDURE RECEIVE(message):
    state ← STATE_FOR(message.streamId)
    seq ← message.sequence

    IF seq < state.expected:
        RETURN                 // Already released: old duplicate

    IF CONTAINS(state.buffer, seq):
        RETURN                 // Already buffered: duplicate

    INSERT(state.buffer, seq, message)

    WHILE CONTAINS(state.buffer, state.expected):
        ready ← GET(state.buffer, state.expected)
        REMOVE(state.buffer, state.expected)
        ENQUEUE(state.displayQueue, ready)
        state.expected ← state.expected + 1

PROCEDURE UPDATE_CHAT(streamId):
    state ← STATE_FOR(streamId)
    WHILE NOT IS_EMPTY(state.displayQueue):
        message ← DEQUEUE(state.displayQueue)
        DISPLAY(message.payload)

EXAMPLE:
    RECEIVE(message #3)  → buffer {3},     displayQueue []
    RECEIVE(message #1)  → buffer {3},     displayQueue [1]
    RECEIVE(message #2)  → buffer {},      displayQueue [1, 2, 3]
    UPDATE_CHAT(stream)  → visible order: 1, 2, 3

08) Missing messages, retries and acknowledgements

Consider arrivals 1 and 3 when message 2 is lost. Message 1 appears, but message 3 waits. The receiver cannot safely invent message 2 or silently skip it while claiming exact ordering. The sender can retain unacknowledged messages and resend them after a timeout. A receiver can report the highest consecutively accepted sequence, or explicitly request missing sequence 2. Duplicate suppression is essential because acknowledgements can also be delayed or lost. Define what “acknowledged” means. An acknowledgement for temporary receipt is different from one for durable storage or committed delivery. If the receiver acknowledges before saving state, a crash may lose data that the sender believes is safe. This pause is called head-of-line blocking: one missing earlier message delays all later messages in the same ordered stream. It is the cost of strict ordering. Independent streams can continue while the affected stream waits. If a message permanently cannot be delivered, the product needs an explicit recovery policy. It may show a delivery error and halt the stream, or introduce an agreed gap marker. Skipping without such a policy changes the original guarantee.

09) Reconnections, persistence and duplicates

A reconnect should not automatically reset expected to 1 while continuing the same stream. Old packets could then be mistaken for new messages, and newly assigned numbers might collide with earlier ones. Two common designs are: persist and resume the existing stream’s sequence state, or create a fresh stream identifier for the new session. If sessions are separate streams, ordering across them still needs a defined reconciliation rule. Persist the sender’s next number and outstanding messages if they must survive a crash. On the receiver, persist committed progress and any necessary buffered messages. Coordinate advancing expected with committing the message so a crash cannot leave progress ahead of stored data. Retries commonly produce at-least-once transport behavior: the same message may arrive multiple times. The ordering layer can suppress duplicates within its remembered stream state, but this alone does not guarantee exactly-once side effects across crashes. For external actions, such as issuing a notification, use idempotent operations or durable deduplication records. A useful message identity is the tuple (conversation ID, sender ID, stream ID, sequence number). This distinguishes message 3 in one conversation from message 3 in another.

10) Complexity and choosing the right container

A FIFO queue implemented with a deque supports enqueue and dequeue in O(1) time. A hash-map reorder buffer supports insertion, duplicate checks and lookup of expected in O(1) expected time per operation. One receive call may release k waiting messages, so its work is O(k + 1) expected. Across n processed arrivals, each accepted message is inserted at most once and removed at most once; total expected processing is O(n). These bounds assume well-behaved hashing and do not include network, storage or rendering costs. Buffer space is O(b), where b is the number of messages waiting behind gaps. Sender retry storage is a separate cost. If missing messages never arrive and later traffic continues, an unbounded buffer can grow indefinitely. Set a maximum receive window, message-size limit and buffer capacity. Reject or defer packets far beyond expected and ask the sender to retransmit within the allowed window. Report this condition rather than silently dropping messages while promising reliable delivery. A min-heap can reveal the smallest buffered sequence, with O(log b) insertion and removal, but it still needs gap detection and duplicate handling. A hash map is simpler when the main operation is “does the exact expected number exist?”. A fixed ring buffer is another option for a bounded sequence window, provided wraparound is handled carefully.

11) Test cases and common mistakes

Test normal arrivals 1 → 2 → 3: every message should be released immediately. Test reversed arrivals 3 → 2 → 1: nothing should appear until 1 arrives, then the entire consecutive block should be released. Test duplicates before and after release. For 3 → 3 → 1 → 2 → 2, message 3 should occupy only one buffer entry and message 2 should appear only once. Test a gap such as 1 → 3: the visible output must stop at 1. Test multiple streams with overlapping sequence numbers. Asha’s message 1 and Ravi’s message 1 must not overwrite one another. Test reconnect behavior and invalid sequence numbers, including negative numbers, oversized values and numbers outside the receive window. Common mistakes include sorting only the packets currently available and displaying all of them, using arrival order as send order, incrementing expected before committing delivery, and resetting counters without a new stream identity. 12) Conclusion

Data structure: use a FIFO sender queue, unique sequence numbers within each stream, and a hash-map reorder buffer at the receiver. Maintain an expected counter identifying the next message that may be displayed. Algorithm: enqueue messages in creation order and attach increasing sequence numbers. At the receiver, ignore already displayed duplicates, buffer new arrivals, and repeatedly release the message numbered expected while it is present. Increment expected after each release and stop at the first missing number. Example: for arrival order 3 → 1 → 2, buffer 3, display 1, then display 2 and buffered 3. The final chat order is 1 → 2 → 3. Complexity: O(1) expected map work per insertion or lookup; O(k) expected work to release k messages; O(n) expected total processing over n arrivals; O(b) receiver buffer space. Retries, durable state and a receive-window limit support a practical implementation. The queue preserves the sender’s local order, sequence numbers identify that order, and the reorder buffer delays early arrivals until the missing prefix is complete. Together they solve the ordering problem; retransmission and durable state address delivery and recovery.
